# Pylentra 0.3.0 — Piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** snippet (palette e gestione), note per connessione con ricerca
estesa, jump host a più salti nell'import, icona nuova, stato della finestra
ricordato.

**Architecture:** il core riceve `snippets.rs` (modello + `SnippetStore`, sullo
stampo di `ConnectionStore`), il campo `Connection.notes` e il collegamento
delle catene in `ssh_config.rs`; `src-tauri` aggiunge tre comandi sottili e il
plugin della finestra. L'interfaccia aggiunge uno store, un modulo puro
`lib/snippets.ts` e tre componenti (`SnippetPalette`, `SnippetForm`,
`settings/SnippetsSection`).

**Tech Stack:** come la 0.2 (Rust 2024, ts-rs 12, Tauri 2, Svelte 5,
xterm.js 6, Vitest). Unico crate nuovo: `tauri-plugin-window-state`.

**Spec:** `docs/superpowers/specs/2026-10-25-v0.3.0-design.md`, da leggere
insieme a questo piano. I riferimenti `§n` sono sezioni della spec.

## Global Constraints

- Unico crate nuovo: `tauri-plugin-window-state = "2"` in `src-tauri/Cargo.toml`. Nessun pacchetto npm nuovo.
- Ogni testo visibile passa da `t()`; ogni chiave nuova va in `ui/src/lib/i18n/en.ts` **e** `it.ts`.
- I binding TS si rigenerano con `cargo test -p pylentra-core` e si committano (`ui/src/lib/bindings/`); la CI fallisce se non aggiornati.
- Prima di ogni commit, dalla radice: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `pnpm --dir ui lint`, `pnpm --dir ui check`, `pnpm --dir ui test`. Per `src-tauri` serve `mkdir -p ui/dist`. Build con `CARGO_INCREMENTAL=0` (disco limitato).
- Il core non usa `unwrap`/`expect`/`panic` fuori dai test (lint in `lib.rs`).
- `connections.toml` resta a `CONNECTIONS_VERSION = 2`. `SNIPPETS_VERSION = 1`.
- Limiti: nome snippet ≤ 80 caratteri, testo snippet ≤ 64 KiB (65 536 byte UTF-8), note ≤ 4 KiB (4 096 byte UTF-8); nome e testo non vuoti dopo `trim`.
- Scorciatoie solo Ctrl+Shift: la palette è Ctrl+Shift+P.
- Ordine dei lock in `src-tauri`: prima `state.store()`, poi `state.snippets()`, mai al contrario.
- Nei test Svelte niente `$state` nei file `.ts` (`rune_outside_svelte`): usare `rerender`.
- Commit con il trailer del repository (`Co-Authored-By` e `Claude-Session`), push solo su `claude/awesome-cannon-6elqn5`.

## Review Focus

1. **Snippet con andate a capo Windows o finali (`"ls\n"`, `"a\r\nb"`)** — un `ls` salvato con l'a capo finale non deve eseguirsi senza "esegui subito", e `\r\n` conta come multiriga. Test in Task 3.
2. **La sessione cade con la palette aperta** — la palette si chiude e non invia nulla a una sessione chiusa. Test in Task 5.
3. **Eliminare una connessione quando `snippets.toml` è in sola lettura** — la connessione si elimina comunque; gli snippet restano e l'errore va nel log. Test in Task 2.
4. **`ProxyJump a, b,` con spazi e virgola finale** — si legge come `a,b`. Test in Task 8.
5. **Note di soli spazi o oltre 4 KiB incollate nel modulo** — spazi → nessuna nota salvata; oltre il limite → errore sul campo, niente salvataggio. Test in Task 6 e Task 7.

### Task 8: Jump host a più salti

**Files:**
- Modify: `crates/pylentra-core/src/ssh_config.rs`
- Modify: `ui/src/lib/i18n/en.ts`, `it.ts` (`import.note.ChainedJump`: «Jump host impostato dalla catena di {target}.» / "Jump host set by the chain of {target}."; testo di `import.note.MultiHopJump` invariato)
- Test: `crates/pylentra-core/tests/ssh_config.rs` (dove stanno i test del parser)

**Interfaces:**
- Produces: `ImportNote::ChainedJump { target: String }` (binding `ImportNote.ts` aggiornato).
- Algoritmo (`fn link_chains(candidates: &mut [Candidate], chains: &[(usize, Vec<String>)], saved: &[Connection])`, chiamata dopo la costruzione dei candidati; `chains` raccoglie `(indice del target, salti)` al posto di `notes.push(MultiHopJump)`):
  1. Salti = `v.split(',').map(str::trim).filter(|h| !h.is_empty())`. Uno solo → si tratta come oggi il salto singolo.
  2. Ogni salto si risolve come il salto singolo (prima `saved`, poi i candidati, senza maiuscole). Un salto con `@`, `:` o `/` → nota `JumpNotAlias` sul target; uno sconosciuto → `UnknownJump`; in entrambi i casi il target resta senza jump e la catena si scarta.
  3. Assegnazioni richieste: target → `hn`, `hk` → `hk-1` per k = n…2.
  4. Un salto **bloccato** non può ricevere un jump: è una connessione salvata il cui `jump_via` è diverso da quello richiesto (assente compreso), oppure un candidato che ha un suo `ProxyJump` non vuoto e non `none` (risolto o no, singolo o multiplo) diverso dal richiesto.
  5. Raccolte le assegnazioni di **tutte** le catene, un candidato che riceverebbe due jump diversi è in conflitto per tutte le catene che lo toccano.
  6. Una catena senza salti bloccati né in conflitto si applica: `jump_via` di target e salti, e `ChainedJump { target: <alias del target> }` su ogni candidato che riceve un jump nuovo (non su quelli che già lo avevano uguale). Altrimenti: target senza jump, nota `MultiHopJump`.

- [ ] **Step 1: Scrivere i test** (testo del file come stringa, `parse(text, &saved)`):
  - `multi_hop_builds_chain` — `Host a`, `Host b`, `Host t` con `ProxyJump a,b` → `t.jump_via = b.id`, `b.jump_via = a.id`, `a` senza jump; `b` ha `ChainedJump { target: "t" }`; `t` non ha `MultiHopJump`.
  - `three_hops` — `ProxyJump a,b,c` → t→c→b→a.
  - `spaces_and_trailing_comma` — `ProxyJump a, b,` → come `a,b`.
  - `hop_with_other_jump_conflicts` — `b` ha `ProxyJump x` (x definito) → `t` senza jump con `MultiHopJump`, `b.jump_via = x.id` invariato.
  - `hop_with_same_jump_is_fine` — `b` ha `ProxyJump a` → catena applicata, `b` senza `ChainedJump`.
  - `saved_hop_never_changed` — `b` salvata senza jump → conflitto (`MultiHopJump`); `b` salvata con `jump_via = a` (a salvata) → catena applicata, `t.jump_via = b_salvata.id`.
  - `unknown_hop_notes` — `ProxyJump a,zz` → `UnknownJump { alias: "zz" }`, niente jump.
  - `shared_hops_compatible` — `t1` e `t2` entrambi `ProxyJump a,b` → entrambe applicate.
  - `shared_hops_conflicting` — `t1` `ProxyJump a,b`, `t2` `ProxyJump c,b` → entrambe scartate con `MultiHopJump`, e il risultato è lo stesso invertendo l'ordine dei blocchi.
