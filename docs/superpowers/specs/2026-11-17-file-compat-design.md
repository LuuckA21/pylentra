# Saved-file compatibility guarantee for 1.x (issue #33)

## Intent

Pylentra's goal for 1.0 is to be stable and safe for the people who already use it.
For 1.0 the files Pylentra saves become a promise:

- A newer version always opens the files of older versions and loses nothing.
- Within 1.x, going back to an older 1.x keeps working with read and write access.
- Going back to a 0.x never loses data.

The user decided all three in this conversation.

## Files in scope

| File | Format today | Kind |
|---|---|---|
| `connections.toml` | `version = 3` | connections, groups, forwards |
| `snippets.toml` | `version = 1` (since 0.3.0) | snippets |
| `settings.toml` | no version key | cosmetic settings |
| export file | `format = "pylentra-export"`, `version = 1` | shared library |
| Pylentra's `known_hosts` | OpenSSH format, no version | trusted host keys |

## What holds today, and what breaks the promise

- **Unknown fields survive.** They are kept in an `extra` table on connections, groups, forwards, snippets and settings. Connections v1 and v2 are read and rewritten as v3.
- **A newer version number opens read-only.** This applies to `load_versioned`, used by connections and snippets.
- **Unknown values do not survive.** A value an older version does not know breaks the file:
  - `AuthMethod` and `ForwardRule` are strict tagged enums. One unknown `type` makes `connections.toml` fail to parse. The file is moved aside as corrupt and the app starts with an empty library. The data survives only in the backup.
  - `Settings.theme` is strict. One unknown value makes the whole settings file reset.
  - `terminal_theme` and `cursor_style` fall back to the default (`lenient_or_default`). The unknown value is then overwritten on the next save.

## Goals

1. **Forward compatibility within 1.x.** An older 1.x reads a file written by a newer 1.x and keeps every value it does not understand, unchanged when it writes the file back.
   - **Unknown auth type.** A connection with an unknown auth type is listed in the sidebar with a label meaning "Requires a newer version of Pylentra". It cannot be opened or edited, but it can be moved to another group or deleted. Its data is written back identical.
   - **Unknown forward type.** The connection works normally. That forward is shown with the same label and never starts.
   - **Unknown theme values.** For `theme`, `terminal_theme` and `cursor_style`, the default is used for display. The saved value is not overwritten unless the user changes that setting.
2. **Fixed format numbers for 1.x, raised once at 1.0.**
   - `connections.toml` becomes `version = 4` and `snippets.toml` becomes `version = 2`.
   - These numbers never change again within 1.x. Formats change only by additions that an older 1.x keeps untouched, per goal 1.
   - A 0.x opening a v4 or v2 file opens it read-only, which existing 0.x code already does. Nothing is lost.
   - A file with a number above 4 or 2 (a future 2.0) opens read-only in 1.x, as today.
3. **Backward compatibility test.** The fixtures are written for real by every released version. A test loads them with the current code and checks that everything is preserved, unknown fields included.
4. **The written guarantee** in the README.

## Non-goals and anti-goals

- **Non-goal:** changing released 0.x versions. That is impossible.
- **Non-goal:** settings protection on 0.x. `settings.toml` has no version, so a 0.x may reset it to defaults when it meets a 1.x value. Settings are cosmetic, and the old file is kept aside as today. The README says so.
- **Anti-goal: renumbering formats down**, for example to 1. A 0.x would take `version = 1` for an old file, open it read-write and could rewrite it, losing data.
- **Anti-goal:** any path where an older version silently drops data it did not understand.

## Approaches

**Unknown values**
- **A (chosen): a catch-all "unknown" variant that keeps the raw table.** `AuthMethod` and `ForwardRule` each get an unknown variant holding the original TOML. It is deserialized when `type` is not a known one and serialized back verbatim. Only the unknown part is disabled: a known connection with one unknown forward still works.
- **B: keep the whole unparseable connection as an opaque block.** Simpler, but one new forward type would make the entire connection unusable.

**Fixtures**
- **A (chosen): generated by each released version's own code.** For every tag from `v0.1.0` to `v0.10.0`, a small generator uses that version's core API to save a rich library. The resulting files are committed as fixtures.
- **B: written by hand from each version's structs.** Faster, but it is a reconstruction.

## Decided

- **Versions.** `CONNECTIONS_VERSION = 4` and `SNIPPETS_VERSION = 2` from this change on. v1, v2 and v3 connections and v1 snippets still load and are rewritten at the new number.
- **Unknown variants.**
  - Defined for `AuthMethod` and `ForwardRule`. They round-trip byte-for-byte at the TOML value level: the same table, with key order as `toml` serializes it.
  - Every code path that matches on these enums handles the unknown variant: connect, jump chains, forward start, the editor and export.
  - **Connecting** to a connection with an unknown auth type fails with a clear error code. The code is new, and its en/it text means "requires a newer version of Pylentra".
  - **Jump chains:** a chain that goes through such a connection fails with the same error.
  - **Forwards:** an unknown forward never starts, even with auto-start. It is listed with the label.
- **UI.**
  - The sidebar row of a connection with an unknown auth type shows the label. Open and Edit are disabled with that reason, Move and Delete work, and accessibility text carries the reason.
  - In the forwards panel, an unknown forward shows the label and has no start button.
- **Themes.** `theme` becomes lenient like the other two. All three keep the raw unknown string, so a save writes it back unless the user changed that setting.
- **Export file.** It becomes `version = 2` at the same time, so a 0.x refuses it with the existing "unsupported version" message instead of misreading it. Importing an export written by a newer 1.x keeps unknown connections and forwards as unknown, and the import preview marks them with the label. Export v1 files still import.
- **Pylentra's `known_hosts`.** The format is OpenSSH's and does not change. The fixture test only proves that each version's file still loads with the same entries.
- **README.** The guarantee, in "Known limitations" or its own short section:
  - 1.x always opens files from older versions without losing anything.
  - Within 1.x, an older version reads and writes files from a newer one and keeps what it does not understand.
  - A 0.x opens a 1.x library and snippets read-only, and may reset settings.
  - A future 2.0 file opens read-only in 1.x.
- **CHANGELOG.** The format numbers rise, and going back to 0.x becomes read-only.

## Left to the builder

- **Fixture generator.**
  - It is one throwaway program per tag, built against that tag's `pylentra-core` in a scratch worktree, never in the user's checkout.
  - It saves the richest library that version can express: groups, jump hosts, every auth type, every forward type, colors, icons, notes, snippets including run and connection-bound ones, non-default settings, an export file where the version has export, and a `known_hosts` with a few entries.
  - Commit the outputs under `crates/pylentra-core/tests/fixtures/compat/<tag>/`, together with a short README there that says how they were made.
  - Commit the generator sources too, so the fixtures can be reproduced.
  - Versions whose output is byte-identical to the previous one may be deduplicated. The test still covers every tag.
- **Fixture test.**
  - For each tag, copy the fixtures to a temp dir and load them with the current stores.
  - Assert the expected content: counts, a few named fields per entity and every unknown field. Then save, reload and assert again.
  - Saved files carry the new version numbers.
- **Forward-compat test.**
  - Hand-written future files hold an unknown auth type, an unknown forward type, unknown theme strings and unknown fields at every level.
  - They load in the current code. Saving writes the unknown parts back unchanged.
  - The UI shows the label: add a UI test.
- **Implementation.** The exact serde technique for the unknown variant (custom `Deserialize`, or `#[serde(untagged)]` fallback around the tagged enum) and the names of the new variants and error code.

## Builder calls (made by Claude after the builder check; the user can correct them)

- **Unknown fields inside known variants are in scope.** A newer 1.x adding a field to a known auth or forward variant (say `Local.bind_interface`) must survive an older 1.x too: each `AuthMethod` and `ForwardRule` variant gets its own preserved `extra`, owned by the store like the existing `extra` tables. The promise is "nothing you did not understand is dropped", at every level.
- **The store owns all raw data.** Unknown variants and per-variant `extra` stay in the store as TOML; the UI only sees a marker (and the type name for display). Whatever the UI sends back for them is ignored, exactly as the existing `extra` handling does. Editing a connection that has an unknown forward never touches that forward; it is shown read-only in the editor and kept.
- **Export.** Unknown variants travel in the export (they are part of the connection); top-level and per-item `extra` stay excluded from exports as today (deliberate current behaviour, `without_extra`). Import keeps unknown variants as unknown.
- **Fixtures.** Every tag `v0.1.0`…`v0.10.0` is covered. A generator is built with that tag's own locked dependencies and its declared `rust-version` toolchain; if a tag still cannot be built, its fixture is written by hand from that tag's code and the fixture README says so. Byte-identical outputs may be deduplicated.
- **Unknown theme values in the settings screen** show the default as selected, with no extra hint (settings are cosmetic); choosing a value overwrites the stored one. The rule is per field. The TS type of the three fields stays the known union; the raw string lives only in the store.
- **Connections with an unknown auth type** cannot be duplicated and cannot be picked as a jump host in the editor; a chain that already goes through one fails with the "requires a newer version" error.

## Release

This is a format change: the numbers rise and going back to 0.x becomes read-only. It ships in the release the user chooses, as a 0.x before the 1.0 RC (#34) or as part of it, to be confirmed with the user.
